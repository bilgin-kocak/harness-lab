# Lean 4 proving on a pinned miniF2F subset: held-out result

> **DRAFT, under review.** The `reproduce.py` run is still in progress. Do not cite this file
> until this note is gone.

**Status: subset result. The Lean kernel checked every outcome.**

On 40 held-out miniF2F problems, Claude Opus 5.5 (`claude-opus-5-5`, medium effort) was given up
to 3 rounds of Lean's error messages. That raised the verified rate from 0.850 to 0.975:

| Test | Result |
| --- | --- |
| Difference | +0.125 [95% CI +0.042, +0.225] |
| Pre-registered sign test | 8/0, p = 0.0078 |
| Secondary majority-outcome test (McNemar) | p = 0.125, not significant |

This is a result on one fixed subset with one model. It is not a leaderboard score.

**Where the numbers come from:**
- Every held-out statistic below is in
  [`results.json`](../../studies/2026-11-math-minif2f/results.json), which
  `harnesslab study report` computes from the records. The rendered tables are in

- The dev tallies, failure types, stops, per-call counts, costs per problem and times are

## Summary

- **System under test.** The model writes a Lean 4 tactic proof for each miniF2F theorem. The
  Lean 4.24.0 kernel, with Mathlib, checks it.
- **The configurations searched.** All ran on 30 dev problems (the `valid` split):
  - the baseline: one model call, no feedback;
  - F: the baseline plus up to 3 rounds in which Lean's error messages and the failed proof go
    back to the model;
  - F plus one more knob each: lemma retrieval, tactic probes, planning, a 48k-token context, or
    2 retries.
- **Dev outcome.**
  - **Stage 1, 1 repeat:** F and four of its variants proved all 30 problems. F with a 48k
    context proved 29, and the baseline 26. F won the tie as the cheapest per verified proof.
  - **Combine:** F was already at 30/30, so no addition could beat it by the required 2
    problems, and the combine stage ran nothing.
  - **Confirm:** F and the baseline each got 2 more repeats. Over all 3 repeats, F verified
    89/90 (0.989) and the baseline 83/90 (0.922). In the confirm repeats alone they verified
    59/60 and 57/60. F was frozen.
- **Held-out comparison.** The comparison covers 40 `test` problems, 3 repeats each, with F
  (frozen) against the baseline:

  | | Baseline | F (frozen) |
  | --- | --- | --- |
  | Verified attempts | 102 of 120 (0.850) | 117 of 120 (0.975) |
  | Problems verified at least once (pass@3) | 36 of 40 | 39 of 40 |
  | Problems verified in at least 2 of 3 repeats | 35 of 40 | 39 of 40 |
  | Cost in total / per verified proof | $6.53 / $0.064 | $13.20 / $0.113 |

  - **Primary test (plan A10).** The per-problem verified rate rises by +0.125
    [95% CI +0.042, +0.225]. F is better on 8 problems, worse on none, and 32 tie (exact sign
    test p = 0.0078).
  - **One of the 8 is sampling luck.** On 7 of the 8, at least one F attempt was verified only
    after a feedback round. On amc12b_2021_p18 all three F attempts passed on their first call,
    so that difference is sampling, not feedback. Counted as a tie, the sign test is 7/0,
    p = 0.016.
  - **Secondary test.** McNemar on the per-problem majority outcome: 4 problems flip to
    verified and none flip back, p = 0.125. That is not significant.
- **Verification.** The Lean kernel decided every outcome.
  - The theorem statement is spliced from the untouched problem file.
  - `sorry`, `admit` and new axioms are refused.
  - Only `propext`, `Classical.choice` and `Quot.sound` may appear among the axioms used.
- **Clean run.** No refusals, API errors or harness errors. The held-out phase ran once and is
  complete: 240 of 240 cells. All 704 API calls in the study (15 smoke, 422 dev, 267 held-out)
  were served by `claude-opus-5-5`.

## What was compared

- **Baseline.** Config hash `980e935d0d7e`:
  - one model call, no feedback rounds, no planning, no retrieval, no tactic tools;
  - a 12,000-token context limit.
- **Frozen configuration.** `F`, config hash `37f78cb9d35f`: the baseline with
  `feedback_rounds = 3`. When Lean rejects a proof, or the reply contains none, the model is
  prompted again, up to 3 times, with Lean's first errors and the failed proof. Everything else
  is equal.
- **Objective (dev only, plan A6).**
  - **Feasibility.** A configuration is feasible only if its mean cost per attempt is at most 4×
    the baseline's.
  - **Ranking.** Feasible configurations are ranked by the mean per-problem verified rate.
  - **Ties.** Within 1/30, the lower cost per verified proof wins.
- **How F was chosen.**
  - **Stage 1 could not rank F against its variants.** Five configurations proved all 30
    problems, and F won the tie-break as the cheapest per verified proof: $0.034, against
    $0.041–$0.070.
  - **Every candidate contained feedback.** All configurations except the baseline included
    feedback rounds, so the freeze could only pick feedback (with or without one more knob) or
    the baseline.
  - **The freeze considered only confirmed configurations.** After the confirm stage, the
    freeze considers only F and the baseline. The variants were within the cost cap (1.27–2.15×
    the baseline) but had only one repeat.

## Protocol

1. **Split.** Problems are ranked by `sha256(f"{seed}:{split}:{id}")`. The first 30 of `valid`
   are dev and the first 40 of `test` are held-out.
   - **Leakage checks.** `split.json` records no shared IDs and no shared statements.
   - **Audit.** `harnesslab study check` also audits that no held-out theorem name or statement
     appears in the prompts or in the 233,022-entry Mathlib retrieval index. It ran before the
     smoke test, but its output was not saved. `reproduce.py` now re-runs it ([Reproduce](#reproduce)).
2. **Smoke test.** 3 dev problems, the first three of dev, with the baseline and with every knob
   on, 1 repeat, $0.35. The owner approved the full run after seeing its measured cost and the
   projected total (plan A9).
3. **Search, on dev problems only.** Each stage's plan or decision was written once, when the
   stage started, and committed (`dev/plans/`):
   - **`stage1`:** 7 configurations × 30 problems × 1 repeat. Committed in `4752149`, 8 s after
     its first cell.
   - **`combine`:** it decided to run nothing (`08a1651`).
   - **`confirm`:** F (the stage-1 winner) and the baseline, 2 more repeats each.
     - Its plan was written at 14:15:55Z, when its first cell started.
     - It was committed in `2a1b60f` at 14:30:36Z, after all 120 confirm cells had finished
       (14:30:29Z). Stage 1 fixes the plan's contents: the winner and the baseline.
4. **Freeze.** `freeze.json` records:
   - the frozen configuration and the baseline;
   - the sealed spec sections and the hash of the 330 dev records;
   - the adapter's provenance: model, prices, prompts, verifier and Lean pins;
   - the split's hash.

   The held-out phase re-checks all of these before running a cell. It found no problem.
5. **Held-out, once.** F and the baseline each ran on 40 problems × 3 repeats, in a seeded
   order: 240 cells, with no harness error and no rerun.
6. **Report.** The per-problem verified rate averages the 3 repeats within a problem. The report
   computes:
   - the mean difference with a 95% percentile bootstrap over problems;
   - an exact sign test on the problems that differ;
   - McNemar on the majority outcome (at least 2 of 3 repeats).

## Verifier

The Lean 4.24.0 kernel with Mathlib `f897ebc` decides every outcome (plan A7):

- **Statement.** The model returns only the tactic block. The harness splices it after the
  untouched problem file's `:= by`, so the statement is byte-identical to the benchmark's.
- **Screening.** Before compiling, the proof is screened. It must not contain `sorry`, `admit`,
  `axiom` or other metaprogramming words, or the commands `#eval`, `#exit`, `#print` and
  `#guard_msgs`. Only a few resource `set_option`s are allowed.
- **Pass condition.** A pass needs all of:
  - an error-free compile;
  - `#print axioms` of the theorem listing only `propext`, `Classical.choice` and `Quot.sound`;
  - no timeout (300 s).
- **Red team.** Before any paid run, a red team attacked this verifier with the real Lean 4.24.0
  and Mathlib, and found no false pass. It reported three rejected proofs:
  - only one of them was a valid proof: a denied word inside a comment, rejected by a stated
    rule that the prompt explains to the model;
  - the other two, laid out with a tab or using an unscoped `set_option`, do not compile in Lean
    4.24.0 anyway, so no correct proof is lost.

**What it does not check:**
- whether a miniF2F statement formalizes its informal problem correctly. The port has had
  statement fixes; the pinned commit includes the latest ones.
- anything about the model's reasoning other than the final proof.

## Results on held-out problems

Frozen (F) against the baseline on all 40 problems. Higher is better.

| Comparison | n | Rate baseline | Rate F | Diff [95% CI] | W/L/T | Sign p | Majority only F / only baseline | McNemar p |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| frozen vs baseline | 40 | 0.85 | 0.975 | +0.125 [+0.0417, +0.225] | 8/0/32 | 0.0078 | 4 / 0 | 0.125 |

| Per configuration | Baseline | F |
| --- | --- | --- |
| Verified attempts (pass@1) | 102/120 = 0.850 | 117/120 = 0.975 |
| pass@3 (verified in any repeat) | 36/40 | 39/40 |
| Problems with mixed outcomes across repeats | 5 | 0 |
| Verified on the first model call | 102/120 (0.850) | 99/120 (0.825) |
| API calls per attempt (mean) | 1.00 | 1.225 (99 attempts used 1, 18 used 2, 3 used 4) |
| Median wall time per attempt; model time | 8.2 s; 8.2 s | 15.4 s; 8.8 s (plus in-loop Lean checks, median 6.3 s) |
| Cost per attempt / per verified proof | $0.054 / $0.064 | $0.110 / $0.113 |
| Refusals | 0 | 0 |
| `max_tokens` stops | 4 | 12 |

**Reading.**
- **The feedback rounds are where the gain comes from.**
  - F's first call uses the same prompt as the baseline, and verified 99 of 120 attempts, close
    to the baseline's 102.
  - In 18 attempts F needed one feedback round, and all 18 were then verified.
  - The remaining 3 attempts used every round on imosl_2007_algebra_p6 and produced no proof.
- **Fresh tries against error messages.** The comparison is not compute-matched: F may make up
  to 4 calls per attempt, the baseline exactly 1, and no configuration with extra fresh tries
  but no error messages was run. So the held-out result alone does not separate the effect of
  Lean's error messages from the effect of extra tries. The round data point to the messages:
  - on aime_1991_p9, amc12_2000_p1 and amc12a_2013_p4, fresh first calls were verified 1 time in
    18;
  - all 8 F attempts there that received Lean's error were verified on the next call.
- **Secondary test.** The majority-outcome McNemar test is not significant (p = 0.125). With 4
  discordant problems, that is the smallest value the exact test can give.
- **Cost.** In total, F cost 2.0× the baseline on held-out ($13.20 against $6.53), and 1.76× per
  verified proof ($0.113 against $0.064). Most of that difference is one problem that neither
  configuration proved:
  - **imosl_2007_algebra_p6.** Each F attempt there made 4 calls that all hit the 32,000-token
    limit. They cost $7.74, which is 59% of F's held-out cost, and took half of F's wall time.
  - **Without that problem,** F cost 1.19× the baseline in total, and 1.04× per verified proof
    ($0.047 against $0.045).
  - **Per problem,** F was cheaper on 15 and more expensive on 24 (sign test p = 0.20). The
    geometric-mean cost ratio is 1.11 [0.96, 1.28].
  - **On dev,** F cost 1.17× the baseline per attempt.

## Cost and latency

- **API cost:** $34.01 of the $150 cap (smoke $0.35, dev $13.93, held-out $19.73).
  - Costs are computed from the token usage the API reported, at a price table copied on
    2026-11-03 from a cached model table. Per million tokens: $4 input, $20 output, $0.20 cache
    reads, $5 for 5-minute cache writes.
  - Plan A8 required a re-check against the live pricing page before the first paid call, and
    no such check is recorded (see Deviations). If the live prices differ, every cost here
    changes in proportion.
  - The costs were not reconciled with the Anthropic invoice.
- **Held-out spend against its reserve.** The held-out phase cost $19.73. That is $2.20 more
  than its $17.53 reserve, and 1.76× the plan-count projection of $11.22.
  - 16 calls stopped at the 32,000-token limit and cost $10.32, 15 of them on
    imosl_2007_algebra_p6. The smoke problems never came near that limit.
  - The $150 cap was never at risk.
- **Time:**

  | Phase | Window (UTC) | Cell-hours |
  | --- | --- | --- |
  | Dev | 13:37–14:30 | 3.36 |
  | Held-out | 14:30–15:30 | 3.07 |

  Four attempts ran in parallel, with up to 3 Lean processes.
- **Per held-out attempt:** median wall time 8.2 s for the baseline and 15.4 s for F, of which
  model time is 8.2 s and 8.8 s. The final Lean check adds a median of about 6 s more: 6.3 s for
  the baseline, 6.0 s for F.

## Failures

**Held-out, F:** 3 failures, all on imosl_2007_algebra_p6. No proof was produced: all 12 of its
calls there stopped at the token limit.

**Held-out, baseline:** 18 failures, on 9 problems:
- 14 Lean errors. Examples: unsolved goals on amc12a_2013_p4, `maximum recursion depth` on
  amc12_2000_p1, a cast mismatch on aime_1991_p9.
- 4 with no proof produced: 3 on imosl_2007_algebra_p6 and 1 on imo_1997_p5. These are the
  baseline's 4 `max_tokens` stops.

`tables.md` lists every failed cell with Lean's message.

**Dev:** 9 failures out of 330 cells.
- In stage 1: 4 baseline Lean errors, and 1 F + 48k-context attempt (see Negative results).
- In confirm: 1 F and 3 baseline Lean errors.
- No refusal, no API error and no harness error in any phase.

## Negative results

- **Dev was at its ceiling, so no other knob is shown to help.** F and four of its single-knob
  variants each proved all 30 dev problems on one repeat. Dev could not tell apart retrieval,
  tactic probes, planning or 2 retries, which all cost more than F.
- **The 48k-context knob was never exercised.** No prompt in any phase exceeded about 2,340
  estimated tokens, and nothing was cut, so F with a 48k context built exactly F's prompts. Its
  run is a second sample of F, not a test of the knob.
  - It proved 29 of 30. Its one failure (mathd_numbertheory_709) had a Lean error and two 120 s
    in-loop timeouts, then its last proof timed out at the 300 s final check.
- **Hard problems.** One held-out problem, imosl_2007_algebra_p6, was not proved by either
  configuration in any repeat.

## Deviations from the plan

- **Plan A13**, recorded before any paid call:
  - API failures that say nothing about the configuration count as `unavailable` (a harness
    error), not as failed proofs. None occurred.
  - The key and the endpoint are explicit, and the key is read from
    `HARNESSLAB_ANTHROPIC_API_KEY`, because cloud sessions hide `ANTHROPIC_API_KEY`.
- **Prices were not re-checked against the live pricing page** before the first paid call, as
  plan A8 required. The table used is from a cached model table of 2026-11-03.
- **Held-out reserve.** Before stage 1 it was set to $17.53, from the smoke test's upper-bound
  projection (1.25 × $14.03).
  - The all-knobs-on configuration stood in for the frozen one, which was not yet chosen. Plan
    A9 bases the reserve on the dev costs of the baseline and the frozen configuration.
  - Held-out spending then exceeded the reserve by $2.20 (above), without coming near the cap.
- **Not searched:** effort levels other than `medium`, other models, and a configuration with
  extra fresh tries but no error messages. The plan fixes one model and one effort level.
- **Operational fix during the run, no effect on any record.** After the smoke run,
  `harnesslab study search` exited with code 1 because it closed the SDK client on another event
  loop. It was fixed in `531e810`, before stage 1.

## Limitations

- **Contamination.** miniF2F is public and older than the model, so the model may have seen
  these problems or their solutions.
  - Absolute rates (0.85 and 0.975) may be inflated by memorization.
  - The paired comparison (same model, same problems) is less affected, but it is not immune.
    Memorization can interact with feedback: a memorized proof needs no feedback, and an error
    message may help the model recall a public proof (plan A12).
- **Not compute-matched.** F may make up to 4 calls per attempt; the baseline makes 1 (see
  Reading).
- **Small subset.**
  - 40 held-out problems, 3 repeats, one model, one effort level and one Lean version.
  - The rates are near the ceiling: 31 of the 32 tied problems were verified in all 6 attempts
    by both configurations.
- **The search found the plan's reference configuration.** F, the baseline plus feedback, was
  named in the plan. Every other candidate also contained feedback, and dev could not separate
  them. The held-out result tests feedback, not a configuration discovered by search.
- **Sampling is not seedable.** A rerun of the attempts would give different proofs, so the
  repeats measure that variability. `reproduce.py` re-checks the recorded proofs and statistics;
  it does not re-sample.
- **Costs are at an unverified list-price table**, not invoice amounts (see Deviations).

## Reproduce

```bash
bash studies/2026-11-math-minif2f/setup.sh
export PATH="$HOME/.elan/bin:$PATH"
uv run python studies/2026-11-math-minif2f/reproduce.py <miniF2F-lean4 checkout at 5746b7d> --reverify all
```

The script makes no API call. It checks seven things, and prints PASS or FAIL for each:
1. It re-derives `split.json` from the checkout.
2. It re-checks every freeze check, except that `freeze.json` is committed: its scratch copy is
   not a git checkout. Check that one with
   `git log -- studies/2026-11-math-minif2f/freeze.json`, which shows `267eb70`.
3. It re-runs the leakage audit of `study check`.
4. It recomputes the held-out comparison from the committed records.
5. It checks that the held-out phase is complete.
6. It checks the total spend against the cap.
7. It re-checks every recorded held-out proof with the Lean kernel.
